# ETL госзакупок РК и аналитический интерфейс — проектирование

## Цель

Создать production-ready проект на Python 3.10+, который получает сведения OWS v3 государственных закупок РК через GraphQL, сохраняет данные за 2024–2026 годы для заданного списка БИН в PostgreSQL и предоставляет аналитический интерфейс Streamlit. Проект должен запускаться в Docker Compose, поддерживать повторный ежедневный запуск без дублирования записей и не хранить секреты в исходном коде.

## Границы первой версии

- Источники: организации, пункты планов, лоты и договоры OWS v3.
- Транспорт реестров: GraphQL с курсорной пагинацией `extensions.pageInfo` (`hasNextPage`, `lastId`, `limitPage`).
- Точные поля GraphQL пока неизвестны, поэтому запросы хранятся отдельно и легко заменяются после получения токена и проверки схемы.
- Данные сохраняются только для 27 целевых БИН и периода 2024–2026 годов.
- ИИ-чат не вызывает внешний LLM: `run_ai_agent` возвращает безопасный mock SQL и пояснение.
- Планировщик внутри проекта не нужен: ETL оформляется как отдельный контейнер/команда, пригодная для запуска cron, Airflow или другой внешней системой каждые 24 часа.

## Архитектура

Docker Compose поднимает PostgreSQL, Streamlit и запускаемый по требованию ETL-контейнер. `database.py` содержит SQLAlchemy-модели, создание схемы и пакетный PostgreSQL UPSERT. `etl.py` отвечает за GraphQL-клиент, пагинацию, нормализацию, фильтрацию, преобразование API-объектов и загрузку. `app.py` содержит только UI и параметризованные аналитические запросы. GraphQL-документы располагаются в `queries/`, чтобы адаптация к фактической схеме не требовала переписывать клиент.

Конфигурация читается через `python-dotenv`: `OWS_API_URL`, `OWS_API_TOKEN`, `DATABASE_URL`, параметры timeout, retries и batch size. `.env` содержит пустые/локальные значения и исключается из Git; `.env.example` документирует необходимые переменные без секретов.

## Модель данных

### `dim_subjects`

- `id` — первичный ключ API.
- `bin` — уникальный БИН, индексируемое поле.
- `name_ru`, `name_kz`, `type_supplier`, `system_id`, `index_date`.
- `created_at`, `updated_at` — технические временные метки.

### `fact_plans`

- `id` — первичный ключ API.
- `subject_biin` — внешний ключ на `dim_subjects.bin`.
- `ref_enstru_code`, `count`, `price`, `amount`, `name_ru`, `unit_name`, `publish_date`, `year`.
- Денежные значения и количество используют `NUMERIC`, даты — timezone-aware `TIMESTAMP`.

### `fact_lots`

- `id` — первичный ключ API.
- `customer_bin` — внешний ключ на `dim_subjects.bin`.
- `lot_number`, `ref_enstru_code`, `price`, `amount`, `name_ru`, `description_ru`, `kato_code`, `dumping`, `unit_name`, `publish_date`, `year`.

### `fact_contracts`

- `id` — первичный ключ API.
- `contract_number`, `contract_sum_wnds`, `supplier_biin`, `customer_bin`, `sign_date`, `year`.
- Оба БИН являются внешними ключами на `dim_subjects.bin`.

Идентификаторы API сохраняются без локальной перенумерации. До загрузки фактов ETL получает и UPSERT-ит необходимые организации, поэтому внешние ключи не нарушаются. Для отсутствующего в справочнике, но целевого БИН создаётся минимальная строка организации с этим БИН и техническим идентификатором только после явного логирования; предпочтительный путь — повторить запрос организации и пропустить зависимый факт при постоянной ошибке.

UPSERT выполняется пакетно через PostgreSQL `INSERT ... ON CONFLICT (id) DO UPDATE`; техническое `created_at` сохраняется, `updated_at` обновляется. Индексы покрывают БИН, год, ЕНСТРУ, КАТО и даты.

## Извлечение и пагинация

GraphQL-клиент использует одну `requests.Session`, Bearer Token, JSON content type, connect/read timeout и ограниченный exponential backoff для сетевых ошибок, HTTP 429 и 5xx. Ошибки GraphQL из поля `errors` считаются ошибкой страницы даже при HTTP 200 и логируются без токена.

Пагинатор передаёт `limit` и `after`. После каждой страницы он извлекает коллекцию из `data`, отдаёт элементы пакетами и продолжает с `lastId`, пока `hasNextPage` истинно. Он защищён от бесконечного цикла: пустая страница, отсутствующий или повторяющийся `lastId` при `hasNextPage=true` вызывает контролируемую ошибку.

Отдельные query-файлы определены для subjects, plans, lots и contracts. Mappers принимают как snake_case, так и распространённые camelCase-алиасы. После получения реального токена файлы запросов и таблица алиасов корректируются по introspection/первому ответу без изменения механизма загрузки.

## Очистка и фильтрация

`name_ru` и описание нормализуются Unicode NFKC, управляющие и лишние спецсимволы удаляются, пробелы схлопываются. Значения, состоящие из мусора или маркеров отсутствия (`---`, `н/д`, `нет данных`, `!!!`), преобразуются в `NULL`. Значимые дефисы, точки, скобки, кавычки, символы номера и процента сохраняются.

Единицы измерения очищаются и приводятся к нижнему регистру; известные варианты могут сводиться к одному названию небольшой таблицей соответствий. Числа преобразуются через `Decimal`, даты — в timezone-aware `datetime`; неверные обязательные значения приводят к пропуску записи с причиной в логе.

План сохраняется, если `subject_biin` целевой. Лот сохраняется, если `customer_bin` целевой. Договор сохраняется, если целевой `customer_bin` или `supplier_biin`. Год вычисляется из `publish_date` для планов/лотов и `sign_date` для договоров; разрешены только 2024, 2025 и 2026. Если дата отсутствует, факт не загружается, а причина логируется. До уточнения схемы поддерживаются алиасы дат и единиц (`publish_date`, `publishDate`, `index_date`, `unit_name_ru`, `measure`, и другие явно перечисленные в коде).

## Streamlit

Sidebar содержит выбор БИН и года. Все SQL-запросы выполняются через SQLAlchemy `text()` с bind-параметрами; пользовательский текст никогда напрямую не конкатенируется в SQL.

Главный экран содержит:

1. Поиск аномалий: средняя цена по `ref_enstru_code` в выбранной выборке, отклонение каждого лота от средней и вывод строк с абсолютным отклонением более 30%. Нулевые/отсутствующие цены исключаются.
2. Оценка справедливости: цена лота выбранной организации и КАТО сравнивается со средним и медианным уровнем других заказчиков для того же ЕНСТРУ, КАТО и года.
3. Анализ объёмов ТРУ: количество из планов агрегируется по ЕНСТРУ и годам 2024–2026; рассчитываются год-к-году изменения, а резкими считаются изменения не менее 50% при ненулевой базе.

Чат хранит историю в `st.session_state`, использует `st.chat_input()` и `st.chat_message()`. Mock-агент возвращает демонстрационный параметризованный SQL-шаблон и предупреждает, что запрос не исполняется автоматически.

## Надёжность и наблюдаемость

- Структурированные логи содержат endpoint/query, номер страницы, число полученных/отфильтрованных/загруженных записей и причины отбраковки, но не токен.
- Транзакция ограничена одним UPSERT-батчем, поэтому сбой не откатывает уже успешно загруженные страницы.
- Ненулевой код выхода ETL сигнализирует оркестратору о полном сбое.
- Повторный запуск безопасен благодаря UPSERT по API ID.
- PostgreSQL имеет health check; UI и ETL ждут готовности БД.

## Безопасность

- Все секреты поступают только из окружения/`.env`.
- `.env`, локальные дампы и кэши исключены из Git и Docker context.
- Docker-контейнеры приложения запускаются от непривилегированного пользователя.
- HTTP timeout обязателен, TLS-проверка включена и не отключается конфигурацией.
- SQL аналитики параметризован; mock-агент не выполняет сгенерированный SQL.

## Тестирование и приёмка

Unit-тесты покрывают очистку текста и единиц, разбор чисел/дат, правила фильтрации, алиасы полей, завершение и защиту пагинации, а также форму аналитических запросов. Интеграционный тест PostgreSQL проверяет создание связей и повторный UPSERT без дублей; он маркируется отдельно и запускается при доступном тестовом PostgreSQL. HTTP-клиент тестируется через имитацию ответов, включая 429, GraphQL errors и некорректный курсор.

Готовность первой версии подтверждается следующими проверками:

- `pytest` проходит без реального токена.
- `docker compose config` успешно валидирует конфигурацию.
- `docker compose up -d db app` поднимает здоровую БД и Streamlit.
- `docker compose run --rm etl` сообщает об отсутствующем токене понятной ошибкой, а с токеном запускает GraphQL-загрузку.
- Повторный ETL-запуск обновляет существующие API ID и не создаёт дубликаты.
